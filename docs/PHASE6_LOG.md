## GATE 1 — 오리지널 마스터 3D 캐릭터 "Neon Courier"

| 항목 | 내용 |
|---|---|
| 진행 GATE | 1. 산출물과 검증은 완료했다. **다음 Gate 진입은 사용자 이미지 승인 후다.** |
| 목적 | 블록 인형(프리미티브 91개, 강체 스키닝)을 연결된 곡면, 가중치 스키닝, GLB 캐릭터로 교체하기 위한 원본을 만든다. |

### 제작 방식

Blender 5.2.3 LTS(포터블)를 headless로 실행해 Python 스크립트로 만든다.

1. **몸체·의상:** Skin 모디파이어로 연결된 헐을 만들고, Subdivision으로 매끄럽게 한 뒤, 부위별 목표 삼각형 수까지 Decimate한다.
   - 그다음 색 경계 평면으로 bisect해서 경계선을 깔끔하게 만들고, 팔레트 UV를 지정한다.
   - 데시메이트를 UV 지정 **전에** 하므로 색이 번지지 않는다.
2. **헤어:** 테이퍼 베지어 튜브 8개(비대칭 스우프, 카울릭, 뒤쪽 볼륨)와 캡으로 만든다. 원뿔을 방사형으로 배열하지 않았다.
3. **리그:** CharacterRig.ts와 같은 22본 이름과 계층을 쓴다. 팔은 A-pose(42°)다.
   - **Blender bone heat** 자동 웨이트를 쓴다. 이번 빌드에서 heat가 실패해 fallback한 정점은 0개다.
   - 액세서리(주머니, 무릎 패드, 칼라, 커프스, 지퍼, 패치)는 KD-tree로 가장 가까운 헐 정점의 웨이트를 받는다. 그래서 몸에서 떨어지지 않는다.
   - 머리카락, 신발, 장갑, 탱크, 총은 소켓 본에 강체로 붙였다.
4. **본 정렬:** 웨이트를 계산한 뒤 모든 본을 +Z(roll 0)로 정렬한다. 그래서 GLB 조인트의 rest 회전이 **identity**다. 기존 절차적 애니메이션 코드와 같은 규약이다.
5. **텍스처:** 1024×512 아틀라스 하나에 팔레트 셀 22개, 얼굴 표정 타일 4개(neutral, blink, happy, surprised), 팀 엠블럼이 들어 있다.
   - ORM(거칠기·금속)과 Emissive(LED, 탱크 액체)는 별도 맵이다.
   - 팀 전환은 블루·오렌지 아틀라스를 교체해서 한다(공유 재질 캐시).

### 남은 결함·한계

1. **신발 밑창이 걸을 때 평평한 판처럼 보인다.** 발끝 굽힘 본이 없고 밑창이 강체다. Gate 4에서 toe 보조본을 넣거나 밑창 형상을 고친다.
2. **얼굴 표정 타일 4종은 아틀라스에 있지만 런타임 전환은 아직 없다.** UV 오프셋 셰이더 청크로 Gate 4에서 구현한다.
3. **애니메이션은 아직 기존 절차적(사인파) 모델을 GLB 본에 이식한 것이다.** 키프레임 클립과 state graph는 Gate 4 범위다.
4. **팀 색 외 개인화(피부 5톤, 헤어 색, colorVariant)는 아직 없다.** Gate 3 의상 시스템에서 팔레트 행을 교체하는 방식으로 넣는다.
5. **휴식 자세(A-pose)에서는 총이 가슴 앞에 떠 있다.** 게임에서는 IK로 잡으므로 문제없다.
6. **의상 GLB 5종과 베이스는 만들고 계약 검사도 통과했다.** 하지만 개별 착용 시스템은 Gate 3 범위다.
7. **팔레트 명도를 게임 조명 기준으로 한 번 올렸다**(Blender 스튜디오 조명에서는 밝아 보였다). 실제 게임 맵에서 최종 대비를 다시 검수해야 한다.
8. Blender는 시스템에 설치하지 않았다. 포터블 경로 `C:\Users\user\tools\blender-5.2.3-windows-x64\blender.exe`를 쓴다.

## GATE 2 — GLB 캐릭터 실제 게임 교체 (기존 기능 불변)

| 항목 | 내용 |
|---|---|
| 진행 GATE | 2 (완료) |
| 목적 / 비교 기준 | 오프라인·온라인 게임의 모든 플레이어를 GLB 아바타로 교체한다. 판정, 페인트, 네트워크는 바꾸지 않는다. 비교 기준은 Gate 0 baseline(`docs/screenshots/phase6-baseline/`)이다. |
| 실행 환경 | Windows 11, Intel Graphics (ANGLE D3D11, `0x0000A7AC`), Chrome headless(GPU), 1366×768. 2026-11-06 09:50–10:05 (KST) |

### 구조

```text
Game ──create(team, seed)──▶ AvatarFactory ──▶ SwitchableAvatar (root 고정, Game이 destroy/enabled 사용)
                                │                    └─ inner: CharacterRig(legacy) → GlbAvatar (로드 완료 시 즉시 교체)
                                └─ AvatarLibrary.load(): LOD0~2 GLB + 오렌지 텍스처 (한 번만)
```

- **즉시 반환:** 생성은 기다리지 않는다. 로드 중에는 legacy 리그로 그리다가 로드가 끝나면 살아 있는 아바타 전부를 제자리에서 교체한다. 팀, 승리 포즈, 위치·회전은 교체 시 이어받는다.
- **폴백:** GLB 로드에 실패하면 `status=failed`가 되고 legacy를 계속 쓴다. 게임은 멈추지 않는다.
- **강제 legacy:** `?avatar=legacy`(A/B 비교, 긴급 폴백).
- **공유와 분리:**
  - 메시, 재질, 텍스처, 스켈레톤 템플릿은 라이브러리에서 한 번만 로드한다.
  - 아바타는 각자 스켈레톤 복제본과 **SkinInstance 1개**(LOD 3개 × 프리미티브 2개가 공유)를 가진다.
  - 다른 플레이어끼리 SkinInstance를 공유하지 않는다.
- **팀 색:** 정점 버퍼를 다시 쓰지 않는다. 오렌지 재질을 한 번만 만들어 캐시하고 바꿔 끼운다.
- **LOD:** 품질 프로필의 `characterLodDistance` 기준으로 고른다.
  - LOD0: 이 거리 이하
  - LOD1: 이 거리 초과 ~ 2.5배
  - LOD2: 2.5배 초과
  - 그림자는 LOD0만 드리운다. 1.6배를 넘으면 팔 IK를 생략한다.
- **총구:** GLB의 `muzzle` 노드를 쓴다. 기존 리그와 0.1mm 이내로 일치한다(Gate 1).
- **판정 불변:** 서버, `packages/shared`, 페인트, 프로토콜 코드는 바꾸지 않았다.

2. 처음 보는 조합은 파일 로드와 병합이 끝날 때까지(처음 약 0.4초, 캐시 후 수 ms) 이전 외형으로 보인다.
3. `colorVariant`는 `graphite` 한 종류뿐이다. 피부톤과 헤어 색 변형은 팔레트 행 교체 방식으로 추가할 예정이다.
4. 모자 챙을 정면 눈높이에서 보면 얇은 띠처럼 보인다. 챙 각도는 미세 조정 대상이다.
5. 쇼룸 카메라 배경이 스폰 구역(팀 색 바닥)이다. 전용 쇼룸 배경은 없다.

### 설계

- **전송 형식:** 버전이 붙은 짧은 문자열 `1:h.w.t.b.s.k.g.c`. 슬롯별 허용 목록 인덱스와 색 변형으로 이뤄진다(예: `1:1.1.1.1.0.0.0.0`).
  - `WARDROBE_ITEMS` 목록은 **뒤에 추가만 한다**. 순서를 바꾸면 기존 인덱스의 의미가 달라진다.
  - `isValidLook`은 형식, 길이(≤ 40), 버전, 인덱스 범위가 모두 맞을 때만 참이다. `decodeAppearance`는 잘못된 값이면 기본 외형을 돌려주며 예외를 던지지 않는다.
- **서버** (`MatchRoom`, `schema.ts`):
  - `NetPlayer.look: string`을 추가했다.
  - 입장 옵션의 `look`은 `encodeAppearance(decodeAppearance(...))`로 허용 목록에 맞게 다시 인코딩한다.
  - 경기 중 변경은 `look` 메시지로 받는다. 플레이어당 1초에 1회만 받고, 형식이 잘못됐거나 속도 제한을 넘으면 버리고 `metrics.rejected`에 센다.
  - 이 필드는 시뮬레이션·판정 코드 어디에서도 읽지 않는다.
- **클라이언트** (`OnlineSession`, `Game`):
  - 입장 옵션으로 저장된 외형을 보낸다.
  - 꾸미기 화면에서 저장하면 `setLook()`을 호출한다. 서버 속도 제한 안에서 마지막 요청만 묶어 보낸다.
  - 원격 플레이어의 `look`이 바뀌면 `onActorLook`이 호출되어 그 아바타의 옷을 바꾼다(클라이언트에서도 다시 디코드·검증).
  - 재접속 후 서버 값과 내 값이 다르면 다시 보낸다.
  - 아직 GLB가 로드되지 않은 경우 legacy 리그로 그리다가, GLB로 교체할 때 받은 외형을 적용한다.

## GATE 4 — 키프레임 애니메이션 · 조준 IK · 표정 · 보조 흔들림

### 목적과 비교 기준

- **목적:** Gate 1~3의 코드 사인파 걷기를 Blender에서 저작한 실제 키프레임 클립으로 바꾼다. 표정과 무기별 자세도 추가한다.
- **비교 기준:** 이전 GLB 아바타의 절차식(사인파) 애니메이션.

### 만든 것

**Blender 클립 16종** (`assets-src/blender/scripts/build_anims.py`)

- 산출물:
  - 런타임용: `characters/courier_anims.glb`(251KB)
  - 편집 원본: `colorfront_courier_anims.blend`(클립마다 Action 1개)
- 기본 레이어(절대 포즈): `idle`, `jog`, `run`, `jog_back`, `strafe_L`, `strafe_R`, `dash`, `jump_start`, `jump_air`, `land`, `respawn`, `victory`
- 상체 레이어(rest 대비 델타): `aim`, `fire`, `reload`, `hit`
- 다리 포즈는 해부학적 값(허벅지 스윙, 무릎 굽힘, 발 각도)으로 지정해 키를 찍었다. 걸음 주기는 접지 → 하중 → 중간 → 밀기 → 이륙 → 스윙의 8단계 표다.
- 골반 높이는 다리 각도에서 계산한다. 더 펴진 다리가 바닥에 닿도록 내리므로, 착지·리스폰·승리 웅크림에서 발이 뜨지 않는다.
- 키를 찍는 본은 hips·spine·chest·neck·head·다리뿐이다.
  - 팔·총·탱크는 키를 찍지 않는다. 런타임 2본 IK가 손을 총에 붙인다.
  - root도 키를 찍지 않는다. root motion이 없으므로 **서버 위치를 덮어쓰지 않는다.**

**런타임** (`apps/client/src/avatar/anim.ts`)

- **샘플러:** 엔진 anim 상태 그래프 대신, GLB의 AnimTrack 키 데이터를 직접 샘플링하는 경량 믹서를 쓴다.
- **위상 진행:** 걸음 위상을 시간이 아니라 **이동 거리 / 보폭**으로 진행한다. 서버가 정한 속도(6–8m/s)에 발 주기가 맞는다.
- **방향 블렌드:** 속도 방향 4개(전·후·좌·우)와 jog → run을 크로스페이드한다.
- **공중·대시·전신 원샷:** 공중(jump_start → jump_air)과 대시는 크로스페이드한다. 착지는 낙하 속도에 비례하고 이동 중이면 약해진다. 리스폰과 승리는 전신을 덮는 원샷이다.
- **상체 레이어:** aim, fire, reload(재장전 진행률 동기), hit을 위에 더한다. 조준 피치는 spine·chest·head에 나눠 더한다.
- **원거리 비용 절감:** LOD1은 2프레임, LOD2는 3프레임마다 평가하고(아바타별 위상 분산), 상체 레이어와 IK를 생략한다.

**표정**

- LOD0 병합 메시에서 얼굴 타일 삼각형을 별도의 작은 메시로 분리하고, 표정 4종의 UV 이동본을 만든다(정점 압축).
- 깜빡임(2.2–5.7초 간격), 피격 시 놀람(0.6초), 승리 시 웃음을 표시한다.
- LOD0 드로우콜은 3개(몸, 유리, 얼굴)이고 LOD1/2는 기존과 같다.

**무기별 자세**

- `WEAPON_MODELS`에 다음 값을 추가했다.
  - 모델별 손 위치: 그립과 포그립
  - 들고 있는 위치 오프셋
- 무기별 자세 차이:
  - 샷건은 엉덩이 높이로 낮게 든다.
  - 저격총은 어깨 높이로 높게 든다.
  - SMG는 몸 쪽으로 붙여서 들고, 포그립 대신 탄창을 잡는다.

**보조 흔들림:** 탱크 속 페인트(liquid 본)가 가속도의 반대로 출렁인다. 스프링 k=140, 감쇠 c=7, 최대 ±14°이며 근거리에서만 적용한다.

### 남은 문제

1. **엔진 상태 그래프는 쓰지 않았다.** 거리 기반 위상과 원거리 저빈도 평가가 필요해서 직접 만든 믹서를 썼다. 클립 데이터는 GLB 키프레임 그대로다.
2. **발 미끄러짐이 남는다.** 6–8m/s는 다리 길이 0.6m인 캐릭터에게 물리적으로 과한 속도다(보폭 3m/주기). 아케이드 연출 범위로 본다. 발 고정 IK는 넣지 않았다.
3. **프리뷰는 제자리 재생이다.** 점프 장면에서는 높이가 오르지 않는다. 실제 게임에서는 서버 위치가 높이를 준다.
4. **표정은 LOD0에서만 바뀐다.** 멀리 있는 아바타는 기본 표정으로 보인다.

## GATE 5 — 네온 터미널 비주얼 스킨

### 목적과 비교 기준

- **목적:** 충돌 월드와 페인트 판정은 그대로 두고, 맵에 시각 디테일과 랜드마크 3개를 더한다.
- **비교 기준:** Gate 5 이전 화면. 같은 카메라와 같은 페인트 배치로 촬영했다(`captureShots.js`).

### 구현 (`packages/shared/src/map/neonTerminalSkin.ts`)

충돌 솔리드에서 **파생**하는 비주얼 전용 스킨이다. 솔리드 자체는 수정하지 않는다. 모든 항목은 기존 데코와 같은 `DecorItem`이므로 `decorViolations` 검사를 똑같이 받는다.

**1. 모듈 키트 (면에 밀착, 두께 5cm 이하)**

| 대상 | 추가한 디테일 |
|---|---|
| 경계벽 | 8m 간격 기둥(하단 해저드), 전선관, 3m 띠, 상단 코핑, 네온 라인 |
| 건물 | 3.2m 간격 층 띠, 양 끝 우수관, 파라펫 립, 설비 박스 |
| 고지대 절벽 | 5m 간격 리브, 중간 띠, 하단 네온 |
| 컨테이너 | 상·하단 레일, 문 잠금 바, 문 이음매 |
| 높은 기둥 | 해저드 스커트, 네온 모서리선 |

표지판과 겹치는 위치에는 디테일을 넣지 않아 표지판이 가려지지 않는다.

**2. 바닥 변주 (1cm 이하 마킹)**

- 보수 슬래브의 절단선, 배수 그레이트, 신축 이음을 넣었다.
- 페인트 오버레이가 3cm 위에 그려지므로 **페인트가 항상 위에 보인다.**
- 같은 높이의 마킹끼리 겹치지 않게 해서 z-fighting을 막았다.
- 처음에는 단색 패치를 시도했다. 텍스처가 없어서 붙여 놓은 사각형처럼 보였기 때문에 윤곽선 방식으로 바꿨다.

**3. 랜드마크 3개 (모두 플레이어가 닿을 수 없는 위치)**

1. **페인트 정제소:** 남쪽 블록 지붕(y=5, PLAYER_REACH 3.33m 초과)에 블루·오렌지 탱크와 네온 링, 파이프 다리, 비컨 마스트를 세웠다. 플라자 어디서나 보인다.
2. **항구 등대:** 북쪽 벽 밖(z=−82)에 높이 약 40m의 적백 줄무늬 탑을 세웠다. 다리와 플라자에서 보인다.
3. **컨테이너선:** 남쪽 부두 밖 수면(z 108–126)에 선체, 컨테이너 적재, 브리지, 굴뚝을 배치했다.

**4. 재질:** 기존 데코 재질만 쓴다. 새 재질이 없어서 드로우콜 증가는 최소다.

## GATE 6 — 성능·품질 마감

자세한 결과는 `docs/PHASE6_REPORT.md`에 있다. 요약은 아래와 같다.

- **첫 발사 멈춤:** 118ms에서 11–15ms로 줄었다. 메뉴 중에 이펙트 셰이더를 미리 컴파일한다.
- **자동 해상도:** `ResolutionGovernor`를 추가했다(100% → 85% → 72%, 히스테리시스와 쿨다운). 설정에서 켜고 끌 수 있고 기본은 켜짐이다. 단위 테스트 5개.
- **측정 편차의 원인:** Gate 3–5의 큰 측정 편차는 측정 탭이 백그라운드 상태였기 때문이다. 탭을 앞으로 둔 뒤 3회 반복 측정했다.
  - 로컬 봇 30명: medium p95 **5.3ms(통과)**, low 4.6ms, high 19.2ms(**미통과**, legacy도 25.3ms)
- **실제 온라인 30명**(서버 + 네트워크 봇 29 + 브라우저):
  - 모든 품질에서 rAF가 60Hz를 유지했다(p95 16.9ms).
  - 프레임 작업은 p95 5.5–8.0ms다.
  - 페인트 해시 불일치 0건(2,059회 + 2,929회 검사)
  - 서버 틱 p95 7.5–8.4ms
- **Gate 4 기록 정정:** Gate 4 성능 표의 '미통과' 판정은 이 측정 조건 문제 때문이었다. 같은 조건으로 다시 재면 medium은 통과한다.
