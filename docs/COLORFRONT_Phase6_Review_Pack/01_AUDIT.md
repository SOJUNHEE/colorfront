# 1. COLORFRONT 실제 파일 검토 및 최우선 결정

## 핵심 판정

현재 '규칙·네트워크 검증 기반' 위에 '프리미티브 블록아웃 렌더링'을 올린 상태. 더 많은 광원/SSAO/파티클을 먼저 추가할 이유가 없다. **실루엣·자연스러운 관절·애니메이션·모듈식 맵 형태·착용 시스템** 순서가 합리적이다.

### 문서 및 소스에 기반한 확인

- `docs/GRAPHICS_REPORT.md`는 2026-10-16 시점의 기록이라 '서버 없음'이라고 기재했지만, 2026-10-30 `docs/PHASE3_REPORT.md` 및 현재 `apps/server/src`에는 Colyseus 실제 코드가 존재함. 고쳐야 할 자료 기준은 후자.
- `apps/client/src/player/CharacterRig.ts:26-50`: 현재 계약상 `root`~`liquid` 22본. 이름만 동일하다고 스키닝이 자동 호환되지는 않는다. **계층·rest pose·bind matrices·축·스케일**도 일치해야 함.
- `CharacterRig.ts:144-322`: 프리미티브 부품을 생성. **유기적인 정점 연결과 천·관절 변화가 원천적으로 부족**.
- `CharacterRig.ts:434-479`: 정점별 [1,0,0,0] 가중치와 단일 본 인덱스를 할당. 부드러운 관절 변형 불가.
- `CharacterRig.ts:381-425,482-513`: **캐릭터 인스턴스마다 LOD별 메시와 2개 재질을 생성**한다. 반면 `SkinInstance`는 한 캐릭터 안의 두 레이어/LOD에서 공유한다. 개선 시 공용 `Mesh`·`Skin`·기본 `Material`과 캐릭터별 `SkinInstance`/재질 파라미터를 명확히 분리할 것. **서로 다른 캐릭터의 SkinInstance 자체를 공유하면 안 됨**.
- `CharacterRig.ts:515-530`: 팀이 바뀌면 버텍스 컬러를 갱신하므로 공유 메시 구조로 바꾸기 전 색상 변경 전략이 필요함(공통 텍스처+팀 컬러 파라미터/마스크 등).
- `CharacterRig.ts:609-744`: 정현파 보행 + 코드 기반 IK. 코드가 잘못됐다기보다는, 이 방식만으로 실제 무게 이동과 연기감을 내기는 한계가 큼.
- `apps/client/src/game/Game.ts:217,289,544-565`: 로컬/원격 모두 `new CharacterRig(...)` 후 `update(dt, RigPose, distance, lodDistance)` 호출. **외부 호출 지점을 유지하는 어댑터**가 가장 안전.
- `apps/client/src/scenes/ArenaBuilder.ts:116-188,190-270`: 충돌 세계 솔리드를 시각 기하로 사용하고 정적 장식을 배치하며 머티리얼별 배치. **월드 솔리드 기하나 페인트 표면을 직접 바꾸면 서버/셰이더 불일치 위험**.
- `apps/client/src/settings/settings.ts:47-86`: low/medium/high마다 캐릭터 LOD 전환거리, 장식밀도, SSAO, 그림자 등이 다름. 추가 최적화는 이 품질 옵션과 통합.
- `docs/GRAPHICS_REPORT.md`의 30인 high 값: 드로우콜 261 / 삼각형 약 391k, 과부하일 때 19.8~20.9 ms. 60 fps 고정은 증명 안 됨. 기존 low/high 값도 편차 2~3배.
- `docs/PHASE3_REPORT.md`의 30인 온라인 관전(1280×720)은 53~60 fps이나 화면 내 플레이어는 약 1명. **30명이 한 화면에 모인 온라인 측정 데이터는 없음**. `109/109` 테스트는 보고서 기록이지 이번 환경의 재측정 결과는 아님.
- `tests/visual/paintConsistency.js`: 셀 중심 샘플 비교. 데이터 무결성에 유용하지만 '모든 화면 픽셀과 서버 셀 색 100% 일치'를 보장한다는 의미는 아님. 검증 기준을 셀 중심 + 오버레이/경계+다리 위아래 별도로 강화할 것.

## 2. 3D 제작 접근법 비교

점수는 COLORFRONT 1인·내장 GPU·상용 품질 목적에 대한 상대평가(정량 측정치 아님).

| 방법 | 품질 잠재력 | 실제 비용 | 리깅/스타일 통일 | 라이선스 | 판단 |
|---|---|---|---|---|---|
| (a) Blender Python 코드 생성 | 중간(수작업 보정 필요) | Blender 무료, 시간 투자 | 스켈레톤 규격과 반복작업 일관성 강점 | 자기 제작분 정리 쉬움 | **최종 생성 도구 + 자동화 핵심**. 조형은 AI/사람이 검수 |
| (b) Meshy/Tripo AI 3D | 중간~높음(편차 큼) | 사용한 플랜/크레딧에 따름 | 비정형 토폴로지, retopo/UV/skin 수동 검증 필요 | 플랜별 차이; 입력 IP 주의 | 실루엣 탐색·장식 시안에 활용. 최종 플레이어 캐릭터 원클릭 생산 의존 X |
| (c) Kenney/Quaternius + Mixamo | 배경용 중간~높음 | 무료/팩 구매/정리 시간 | 공통 리깅은 Mixamo 보정 필요 | 팩마다 확인. Quaternius 최신 QAL 별도 주의 | **배경 보조·동작 베이스에 최적** |
| (d) 외주 | 전문 작업자면 매우 높음 | 계약금 + 수정비 + 산출물 관리 | 납품 요건이 정확할 때 가장 좋음 | 소스·상업 사용·재사용 조항 계약 | 1개 마스터 캐릭터만 외주 고려(예산 있으면) |
| (e) 현 코드(SDF/메타볼/스키닝) 개선 | 중간 | 코드 연구 시간 큼 | 런타임 및 LOD 통합 복잡 | 자기 제작분 | 테스트/프리비주얼에는 유용. **주력 최종 아바타 파이프라인으로 비권장** |

**최종 추천: Blender(마스터 `.blend`, 자동화 스크립트) + 직접/AI 제작한 오리지널 조형 + CC0/QAL 확인된 배경 보조 + Mixamo 클립을 리타깃/정리 + GLB 배포.** 예산이 가능하면 오리지널 캐릭터 모델 1종만 외주한 뒤 의상을 자체 파생.

### 라이선스 함정(2026-11-05 검토)

- Kenney 일부 공식 묶음은 CC0로 표기. **팩별 라이선스 원본을 보관**할 것.
- Quaternius FAQ는 CC0라고 안내하지만, **2026-08-28 현재 공식 `license.html`은 QAL v1.0(상업적 게임 사용 허용, 에셋 자체 재배포·재판매 제한)**. CC0라고 일괄 표기하면 안 됨.
- Mixamo는 Adobe 공식 FAQ상 게임 내 상업적 이용 가능. 자동 리깅은 **인간형 이족 보행**에 적합하며 과도한 비율·부착물은 실패 가능. FBX 등 원본을 3D팩으로 재배포하는 문제는 별도 규정 확인.
- Meshy 무료 출력은 CC BY 4.0, 유료는 약관상 조건부 고객 소유. Tripo 무료는 출력 권리가 제약되고, 유료는 상업 이용 가능하다고 공식 안내. **입력 이미지가 타사 IP면 생성 결과도 안전해지지 않음**.
- Nintendo 캐릭터, 특정 머리/얼굴/무기/로고/아이콘/지도/UI를 1:1로 따라하지 말 것. 장르의 페인트 점령, 쾌활한 전투 가독성, 색 대비, 액션 템포는 기능적으로 참고 가능.

## 3. 맵 개선 우선순위(성능 고려)

1. **전투 지점별 랜드마크/중간 실루엣**: 기성 박스 외부를 미관으로 감싸거나 벽면에 구조물 추가. 콜리전·카메라 커버·도색 가능 면 변화 금지.
2. **모듈식 키트와 베벨/트림**: 계단·문·난간·모서리 보호대·물막이·기계 구조물. 배치 지오메트리는 충돌 판정상 무시되므로 캐릭터가 관통해도 어색하지 않은 위치만.
3. **발밑 디테일**: 페인트 표면과 겹치지 않게 UV/텍스처 아틀라스에 균열·웨더링·방향 표시 추가. 오버레이가 페인트를 가리면 실패.
4. **고유 재질/변주**: 모듈 색·거칠기·노멀의 2~3종 변주. 드로우콜을 늘리는 유니크 머티리얼 남발 금지.
5. **조명·라이트맵**: 마지막. 베이크가 가능한 표면만, 동적 페인트에 직접 라이트맵을 덮지 말고 시험할 것. SSAO 강도 증가로 조형 부족을 숨기지 말 것.

## 4. 초기 성능 목표(실측 아님)

### 캐릭터: 스켈레톤+바디+실착 의상+장비 **합계** 삼각형

| 수준 | 화면 크기 예시 | 1명당 목표 | 예시 전환 조건 | 선택 규칙 |
|---|---|---:|---|---|
| LOD0 | 가까운 전투, 100px+ 높이 | 5,000~8,000 | 기본 0~12m 후보 | 화면 점유 기준 우선, 내 캐릭터 예외 |
| LOD1 | 중거리 약 40~100px | 1,800~3,000 | 12~30m 후보 | 눈/얼굴·무기 형태 유지 |
| LOD2 | 먼 거리 12~40px | 500~1,200 | 30m+ 후보 | 손가락·호스·작은 소품 숨김 |
| Culling | 프러스텀 밖/극원거리 | 0 | 카메라 기준 | 팀 구분이나 게임플레이 가독성 훼손 시 조정 |

- 적어도 1개 플레이어 메시 LOD/바디+옷+무기 합산. 의상별로 동일 폴리곤 예산을 추가로 잡지 말 것.
- 원칙: 본은 필요한 것만 변형(기본 22본 호환, 얼굴/머리 보조본은 단계적으로), 정점당 4개 이하 가중치. 리깅을 자동 생성했다고 품질이 좋아지는 게 아님.
- 재질: 기본 아바타 1 atlas + 투명/발광 탱크 선택적 1 + 무기 공통 1 = **2~3회 불투명/혼합 드로우콜/근접 아바타**를 목표로 하되, 투명물은 별도 패스 비용 측정. 실수로 한 의상당 1~3 draw call 추가 금지.
- 30명 전원 LOD0 예외 장면은 캐릭터만 150k~240k tris가 될 수 있어 맵/페인트 포함 60fps 보증 불가. 30명 밀집 테스트에서 GPU/CPU 양쪽을 계측하고 LOD와 품질 자동 조정.
- 공통 텍스처: 캐릭터 1024×1024 atlas(알베도+ORM+노멀, 피부/의상 재활용), 가까운 얼굴/장비 필요한 경우에만 별도 512~1024. LOD2는 256~512 축소 또는 공통 atlas 기반.
- 압축: 우선 **KTX2/Basis Universal**(GPU 환경에 맞게 트랜스코딩, 실제 엔진 설정 검증), **Draco**는 메시 다운로드 크기 개선용 A/B 사용. 정적/스킨드 메시·morph/LODs+호환성 검증. 런타임 드로우콜/tri 비용을 직접 줄이지는 않음.
- 권장 통과 예산(실측 전 가설): 1366×768 Intel 내장 GPU **동일 장면 30인 온라인** medium p95 ≤16.7ms(여유 있으면 ≤15ms 목표), 프레임 낙폭과 전투 시 hitches 기록, 드로우콜은 시작 가이드로 ≤150~180회 내외(그림자 포함 실제 계산법 확인). 실패하면 저품질 LOD/해상도/그림자부터 줄일 것.
