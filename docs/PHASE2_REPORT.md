## 0. 사전 확인: Phase 1 실제 마우스 잠금

지시대로 Phase 2를 시작하기 전에 확인했다.

| 항목 | 결과 |
|---|---|
| "클릭하여 플레이" → 실제 Pointer Lock | **성공** (Chrome 155) |
| 잠금 상태에서 이동·마우스 회전 | 동작 |
| 해제 → 재개 3회 반복 | 3회 모두 정상 |
| 해제 직후(1초 이내) 재클릭 | Chrome이 거부하고, 게임이 "잠시 후 다시 클릭하세요" 안내를 표시함 (의도된 처리) |
| **실제 ESC 키로 해제** | 자동화 도구의 Escape는 브라우저 잠금 해제를 일으키지 않아 **검증 불가**. 사람이 직접 확인해야 함 |

신규 테스트 내용:
- **격자·면적**: Surface 8개와 격자 크기, 도색 가능 55,192셀(71.9%), 스폰·건물·엄폐물·상자 마스크, 다리 아래 바닥은 칠할 수 있음.
- **도색**: 1.2m 원 = 21셀, 같은 팀 재도색 0, 덮어쓰기 ±21, 부분 겹침.
- **다리 위·아래를 서로 다른 색으로 칠하기**(필수 테스트), 다리 아래면 사격이 윗면을 칠하지 않음.
- **고지대**: 상단과 절벽 아래 바닥이 독립적. 절벽 아래쪽을 맞히면 밑동 바닥만 칠해짐.
- 경사로 도색, 격자 경계와 맵 밖 좌표, **1,000회 랜덤 도색 후 증분 카운트 = 전체 스캔**, 모든 셀 소유권 ∈ {0,1,2}, 마스크 셀은 항상 0.
- **히트스캔**: 크로스헤어 지점 정확 착탄, 장애물 정지와 법선, 25m 사거리 낙하, 벽에 붙었을 때 어깨 기준점 당김.
- `stepPlayer`: 1초 연사 6발, 탄약 30, 도색 셀 수 = 블루 카운트.
- **속도**: 걷기 6.9 / 4.8 / 6, 달리기 9.2 / 6.4, 공중 미적용, 아군·적 페인트 위 대시 정확히 4m(이후 미끄러짐 없음).
- **결과**: 셀 수 기준 승패와 무승부(반올림 %가 같아도 셀 수로 판정), reveal → summary → done, 연출 시간 0~15초 제한.

## 4. 브라우저 검증 (Chrome 155, 1366×768, Intel 내장 GPU)

| 확인 항목 | 결과 | 방법 |
|---|---|---|
| 발사하면 정확한 위치에 페인트가 생기는가 | **예** | 착탄점이 화면 정중앙(683,384) = 크로스헤어로 투영됨. 착탄 주변 100개 지점의 화면 픽셀 색과 데이터 소유권 **100/100 일치** (블루, 오렌지 모두) |
| 블루 위에 오렌지 덮어쓰기 | **예** | 같은 지점: 블루 18 → 0, 오렌지 0 → 18. 픽셀도 오렌지로 바뀜 |
| 고지대·다리 위/아래 독립 | **예** | 다리 아래 (0.8, 0, −46) 블루, 바로 위 다리 (0.8, 7, −46) 오렌지. 다리 아래 픽셀 100/100. 고지대 상단 오렌지일 때 절벽 아래 바닥 0셀 |
| 점령률 합계 | **예** | 매 단계 블루 + 오렌지 + 미점령 = 55,192, 증분 = 전체 재계산. HUD % 표시 일치 |
| 도색에 따른 지상 이동속도 | **예** | 6.90 / 4.80 / 6.00 (걷기), 9.20 / 6.40 / 8.00 (달리기), HUD `PAINT x1.15 / x0.80 / x1.00` |
| 대시 거리 일정 | **예** | 아군 페인트 4.0m, 적 페인트 4.0m, 맨바닥 4.0m (실제 Q 키) |
| 공중 보정 미적용 | **예** | 점프 직전 6.90 → 공중 6.00 m/s |
| 기존 카메라·이동 | **예** | 걷기 1초 6m, 카메라 4.2m 뒤 유지, 콘솔 오류 0 |

검증 방법에 관한 사실:
- 실제 Pointer Lock으로 바닥 사격·덮어쓰기를 확인했다. 이후 항목(다리, 고지대, 속도, 대시)은 테스트 중 잠금이 반복해서 풀려서, **테스트에서만 잠금 상태를 고정**하고 키는 실제 키 이벤트로 넣었다.
- 자동화 창이 가려지면 Chrome이 렌더 루프를 거의 멈춘다(초당 1~3프레임). 그래서 속도·대시 측정은 실제 게임 루프 함수 `Game.update(1/60)`를 직접 반복 호출해 시간을 진행했다.
- 위치 배치와 감도 0 고정은 측정용 조작이고, 게임 코드는 바꾸지 않았다.
- **원인 발견:** 측정 중 사격 조준이 흔들리고, 잠금이 풀리고, 캐릭터가 혼자 걸은 원인은 **작업 중 사용자의 실제 키보드·마우스 입력이 앞으로 가져온 자동화 창에 들어간 것**이었다(키 로그로 확인). 위 표의 수치는 모두 기대값과 정확히 일치해서 측정 구간에 간섭이 없었다고 판단한다.
- **사람이 직접 확인해야 할 것:** 실제 마우스로 조준하며 연사하는 손맛, ESC 키 해제, 장시간 플레이.

FPS: 창이 앞에 있을 때 약 58~60 FPS(medium). 도색이 많을 때의 프레임 비용은 측정하지 않았다.

## 6. 알려진 한계

1. 셀이 0.5m 정사각형으로 보인다(계단 모양 가장자리). 랜덤 가장자리 셰이더는 아직 없다.
2. 렌더 위치 보간 때문에 크로스헤어와 실제 착탄점이 최대 1틱 이동량(≈0.3m)만큼 어긋날 수 있다(달리면서 쏠 때).
3. 바닥 Surface 텍스처(320×240)를 바뀔 때마다 통째로 다시 업로드한다. 1인에서는 문제없지만 30인 연사에서는 부분 업로드나 행 단위 업로드가 필요할 수 있다.
4. 시야 검사 비용은 30인 동시 사격 기준으로 측정하지 않았다(GDD 8.1 최악 가정 180발/초).
5. 실제 피해, 리스폰, 경기 시간 흐름, 결과 화면 UI는 없다.
6. 색약 대응은 점령 바의 아이콘·줄무늬까지만 했다. 바닥 페인트 패턴은 아직 없다.

## 7. Phase 3 작업 범위 (2인 권위형 멀티플레이) 제안

1. **서버 생성**: `apps/server` — Node 24 + TypeScript + Colyseus 0.18. 설치 후 실제 타입으로 `Room`, 메시지 API, 고정 틱 API를 확인하고 `protocol/messages.ts` 초안을 확정한다.
2. **권위 시뮬레이션**: 서버 Room이 플레이어별 입력 큐를 30Hz로 처리한다(`sanitizeInput` → `stepPlayer(…, paint)`). 클라이언트는 입력만 보낸다.
3. **페인트 동기화**: 접속 시 `paint:snapshot`(Surface별 owners, revision, CRC), 이후 50~100ms 단위로 묶은 `paint:delta`(revision, 변경 셀). revision 간극을 발견하면 `paint:resync`. 기존 `surfaceRevisions`를 활용한다.
4. **클라이언트 예측과 재조정**: 로컬 예측, `lastProcessedSeq` 이후 입력 재적용. 원격 플레이어는 100ms 보간 버퍼. 예측 도색은 서버가 확정하면 덮어쓴다.
5. **경기 진행**: WAITING → COUNTDOWN → PLAYING(300초) → RESULTS(reveal 5초 + 결과 30초) → CLOSED. 팀 배정은 서버가 하고, 개발용 T 키는 개발 빌드로 제한한다.
6. **피해·리스폰**: 원기둥 히트 판정, 14 피해, 5초 리스폰, 2초 무적(공격 시 해제 여부 결정 필요).
7. **검증 기준(GDD Phase 3 통과 조건)**: 두 브라우저에서 동시에 이동·도색한 결과의 셀 해시가 서버와 완전히 같고, 재접속 후에도 같다.
8. **배포 없음**: 로컬 서버만. Render/Vercel 배포는 별도 승인을 받은 뒤에 한다.
