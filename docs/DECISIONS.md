## D-001 JUDGING 페이즈 없음 — 판정은 RESULTS 안에서 처리
- **승인:** 2026-10-16 (Phase 2 지시)
- **GDD 충돌:** 2.1 "준비 15초 → 전투 300초 → **판정 15초** → 결과 30초"와 2.4 페이즈 목록(판정 단계 없음)이 서로 맞지 않았다.
- **결정:**
  - 페이즈는 GDD 2.4의 5개(WAITING / COUNTDOWN / PLAYING / RESULTS / CLOSED)를 그대로 둔다.
  - **PLAYING이 끝나는 순간 점수를 확정**한다(`finalizeRound`). 승패는 셀 수로 비교하고, 같으면 무승부.
  - RESULTS는 `reveal`(판정 연출) → `summary`(결과·재시작 선택) 두 단계로 나뉜다(`resultsStageAt`).
  - 판정 연출 시간은 설정값 `MATCH_TIMING.resultsRevealSeconds`이다. 기본값은 **5초**(GDD의 15초에서 단축)이고, `createMatchTiming()`이 0~15초로 제한해서 결과 확인이 불필요하게 늦어지지 않게 한다. 결과 표시는 30초.
- **코드:** `packages/shared/src/rules/match.ts`, 테스트 `tests/unit/combat.test.ts` › round result
- **아직 없음:** 실제 경기 진행(타이머, 페이즈 전환)은 Phase 3 서버 Room에서 구현한다.

## D-002 점령 대상 면과 Surface별 독립 격자
- **승인:** 2026-10-16
- **GDD 변경:** 6.1의 "단일 `Uint8Array(76800)`"는 같은 X·Z에 높이가 다른 바닥(다리 위·아래, 고지대)을 표현할 수 없다.
- **결정:**
  - 점수에 포함: 바닥(floor), 고지대(platform), 경사로(ramp), 다리(bridge)의 **윗면**.
  - 점수에서 제외: 벽, 건물, 엄폐물(cover), 경계벽, 그리고 다른 물체에 덮인 셀과 스폰 구역 셀.
  - 칠할 수 있는 고체마다 **0.5m XZ 격자를 따로** 둔다. 경사로도 XZ로 투영하므로 1셀은 항상 0.25m², 1점이다.
  - 셀 소유권은 `0 미점령 / 1 블루 / 2 오렌지` 중 정확히 하나다. 마스크가 0인 셀은 항상 0이다(테스트로 검증).
- **실측(맵 데이터 기준 재산출):**

  | 면 | 격자 | 도색 가능 셀 |
  |---|---|---|
  | 바닥 | 320×240 | 41,472 |
  | 고지대 서/동 | 100×56 ×2 | 5,516 ×2 (상자 2개 제외) |
  | 경사로 ×4 | 16×24 ×4 | 384 ×4 |
  | 다리 | 48×24 | 1,152 |
  | **합계** | | **55,192셀 = 13,798m² = 160×120 면적의 71.9%** |

  GDD의 가정치(약 49,920셀, 65%)보다 많다. 단층 바닥만 세면 54.0%다.
- **코드:** `packages/shared/src/paint/PaintGrid.ts`

## D-003 도색 위 이동속도
- **승인:** 2026-10-16
- **결정:**
  - 아군 페인트 위 ×1.15, 적 페인트 위 ×0.8. 틱 시작 시점에 발 아래 셀 하나만 본다.
  - **지상의 걷기·달리기에만** 적용한다. 공중 이동과 점프 중에는 적용하지 않는다.
  - 배율은 한 번만 곱하고 다른 보너스와 중첩하지 않는다. 달리기에도 같은 배율 하나가 붙는다(8 → 9.2 / 6.4).
  - **대시는 항상 정확히 4m**다. 대시가 끝나면 속도를 현재 입력의 목표 속도로 바로 넘긴다. 그래서 입력이 없으면 4m에서 멈추고, 미끄러지는 거리가 페인트에 따라 달라지지 않는다. (Phase 1에서는 대시 후 0.2~0.4m 미끄러졌다.)
- **코드:** `packages/shared/src/rules/paint.ts`, `simulation/movement.ts`

## D-004 히트스캔과 크로스헤어 기준점 공유
- **결정:**
  - 카메라는 항상 공유 함수 `aimPivot`(머리 높이 1.55m, 오른쪽 어깨 0.8m, 벽에 막히면 안쪽으로 당김) 뒤쪽 직선 위에 있다. 따라서 화면 중앙 크로스헤어 = `aimPivot`에서 시작하는 시선 광선이다.
  - 사격 순서:
    1. 시선 광선으로 조준점을 찾는다.
    2. 가슴 높이 총구(플레이어 자신의 충돌 원기둥 안쪽이라 벽 속에서 발사될 수 없음)에서 조준점 방향으로 사거리 25m 레이캐스트를 한다.
    3. 사거리 안에서 아무것도 맞지 않으면 사거리 끝에서 수직으로 떨어진 지점에 착탄한다.
  - 카메라 줌 거리와 조준(우클릭)은 판정에 영향을 주지 않는다(서버가 재현할 수 있는 값만 사용).
  - Phase 1의 조준 시 어깨 0.85m는 0.8m로 통일했다(크로스헤어와 판정을 일치시키기 위해).
- **코드:** `packages/shared/src/combat/hitscan.ts`, `apps/client/src/player/ThirdPersonCamera.ts`

## D-005 페인트 형상: 3D 구체 + 시야(LOS) 검사
- **결정:**
  - 착탄점을 중심으로 반경 `paintRadius`(라이플 1.2m) **구체** 안에 들어오는 칠할 수 있는 셀 중심을 칠한다.
  - 각 셀은 착탄면에서 0.05m 띄운 점에서 볼 수 있어야 칠해진다. 이것으로:
    - 바닥 착탄 = 반경 1.2m 원.
    - 벽 아래쪽 착탄 = 벽 밑동 바닥 일부.
    - 다리 아래면을 쏴도 다리 윗면은 칠해지지 않는다(0.6m 슬래브 관통 금지).
    - 고지대(7m)와 절벽 아래 바닥은 서로 영향이 없다.
  - 모서리를 스친 사격은 시야 검사에 막혀 아무것도 칠하지 않을 수 있다(의도된 동작).
- **비용:** 1발당 후보 셀 약 25개 × 레이캐스트. 30인 부하는 Phase 5에서 측정한다.

## D-006 "보이는 페인트 = 점수 데이터"
- **결정:** Surface마다 텍스처를 두고 셀 1개 = 텍셀 1개, NEAREST 필터, 알파 테스트로 그린다. 데칼이나 입자는 페인트를 대신하지 않는다. 착탄 링·물방울·트레이서는 순수 연출이다.
- **검증:** 브라우저에서 착탄 주변 100개 지점의 화면 픽셀 색과 데이터 소유권을 대조했다. 바닥 블루·오렌지 100/100, 다리 아래 100/100. 불일치는 화면에 함께 잡힌 장식(네온선, 미처 사라지지 않은 링 이펙트)뿐이었다.
- **한계:** 0.5m 정사각형 셀이 그대로 보인다(계단 모양 가장자리). GDD 6.2의 랜덤 가장자리 연출은 데이터 경계를 넘지 않는 범위에서 이후 셰이더로 추가한다.

## D-010 페인트 셰이더의 데이터 일치 규칙
- 그려지는 페인트는 항상 서버 격자에서 파생된다(D-006 유지). 경계 모양만 장식이다.
- 노이즈 폭 상한: 가장자리 |n| ≤ 0.42 < 0.5, 팀 경계 |m| ≤ 0.8 < 1. 그러면 **모든 셀 중심의 색 = 소유자**가 보장된다.
- 셀 사이의 모양은 장식이다. 셀 중심이 아닌 지점에서는 최대 약 0.2m까지 데이터 경계와 다르게 보일 수 있다.
- 검증 도구: `tests/visual/paintConsistency.js`(셀 중심을 투영해 픽셀을 읽고, 페인트를 켠 화면과 끈 화면의 차이로 판정).

## D-011 날아가는 페인트와 판정 시점
- 판정은 GDD 4.2대로 **즉시 히트스캔**이다(서버 권위, 지연 없음).
- 화면에서는 85m/s 슬러그가 날아간다. 그동안 해당 Surface의 새 페인트 공개만 슬러그 도착 시점까지 늦춘다(최대 0.35초). HUD 점령률은 즉시 갱신된다.
- 이 짧은 순간에는 화면 페인트가 데이터보다 늦게 보인다. 의도된 시각 연출이며, 판정·점수에는 영향이 없다.

## D-015 한 방에서 라운드 반복 (RESULTS → WAITING)
- 결과 화면(공개 5초 + 요약 30초)이 끝나면 방을 닫지 않고 **대기실(WAITING)로 돌아가 다음 라운드**를 준비한다. 상태 전이는 `RESULTS → WAITING | CLOSED`.
- WAITING은 자유 연습 시간이다. 이동·사격·도색이 되지만 점수에는 들어가지 않는다. 모두 준비(G)하면 COUNTDOWN 진입 순간 페인트·스탯이 초기화되고 전원이 스폰으로 돌아간다.
- 라운드 초기화는 전체 격자 델타 대신 **작은 RLE 스냅샷 한 번**으로 보낸다.
- 인원이 최소 인원 아래로 줄면 COUNTDOWN은 WAITING으로 되돌아간다. PLAYING은 인원과 관계없이 시간이 끝나야 끝난다.

## D-016 서버 입력 처리: 모든 입력을 정확히 한 번, 크레딧으로 속도 제한
- **문제(실제 두 브라우저 검증에서 발견):**
  - 처음 구현은 입력이 늦으면 마지막 입력을 무한 반복했다. 탭이 멈춘 플레이어가 서버에서 계속 달리고 쏘았다.
  - 큐를 6개로 자르면 프레임이 끊긴 클라이언트의 입력 묶음이 버려졌다. 서버 위치가 예측과 1~2m 어긋났다.
- **결정:**
  - 클라이언트가 보낸 입력은 순서대로 **모두, 정확히 한 번** 시뮬레이션한다(큐 최대 1초).
  - 플레이어마다 틱당 크레딧 1을 얻고(최대 10) 입력 하나에 1을 쓴다. 늦게 몰려온 입력은 틱당 최대 3개까지 따라잡지만, 길게 보면 실제 시간보다 빨리 움직일 수 없다(스피드핵 차단).
  - 입력이 안 오는 틱에는 **제자리 대기**한다(같은 시선, 이동 0, 사격 버튼 해제, 나머지 버튼 유지).
- **검증:**
  - 통합 테스트 "늦게 몰려온 15틱 입력 → 서버 위치 = 클라이언트 예측(오차 < 1µm)"(옛 방식에서는 1.8m 오차로 실패).
  - 통합 테스트 "입력이 끊긴 플레이어는 멈춘다"(옛 방식에서는 5m 이동으로 실패).

## D-017 상태 동기화 대역폭: 소유자 전용 필드와 압축 이벤트
- 15 vs 15에서 클라이언트당 수신량을 측정하니 29.8KB/s였다. 상태 패치 13.8KB/s, 사격 이벤트 13.7KB/s, 페인트 2.3KB/s로 나뉘었다.
- **소유자 전용 필드(Colyseus 0.18 StateView):** 예측에만 쓰이는 필드는 본인 클라이언트에만 보낸다.
  - 대상 필드: 속도, 사격·대시 쿨다운, 대시 방향, 입력 시퀀스, 무적·부활 타이머(`.view()`).
  - 다른 플레이어의 애니메이션 속도는 보간 위치 차이로 계산한다.
  - 재접속하면 새 Client 객체에 view를 다시 붙인다.
- **사격 이벤트 압축:**
  - 좌표는 cm 정수로 보낸다.
  - 총구 원점은 보내지 않는다. 각 클라이언트가 보이는 총구에서 그린다.
  - 팀은 사격자에게서 알 수 있으므로 생략한다.
  - 착탄점이 비행 끝점과 같으면 생략한다.
- **결과:** 29.8 → 약 15.5KB/s(-48%). 서버 틱 시간은 측정 오차 범위 안이었다(3회 평균 2.2~4.2ms).
- **더 줄일 수 있는 방법(아직 안 함):**
  - 위치를 cm 정수로 보내기. 예측 재조정 정밀도와 맞바꿔야 한다.
  - 원거리 플레이어의 패치 빈도 낮추기.

## D-018 재접속 토큰 저장 시점
- Colyseus SDK 0.18.5는 `onReconnect`를 **새 토큰을 저장하기 전에** 호출한다(Room.mjs 483행 → 485행).
- 그래서 끊김 → 자동 재접속 → 새로고침 순서로 가면 오래된 토큰 때문에 자리를 잃었다. 두 브라우저 검증에서 발견했다.
- 토큰을 마이크로태스크에서 저장하고, `pagehide` 때 한 번 더 저장하도록 바꿨다.
- 새로고침 직후 서버가 아직 이전 소켓의 종료를 처리하지 못했을 수 있다(524 응답). 그래서 0.5초 간격으로 최대 6번 다시 시도한다. 방이 없으면(522) 즉시 포기한다.

## D-019 서버 안정성
- 틱 하나에서 예외가 나도 서버 프로세스 전체가 내려가지 않게 한다. 예외는 로그로 남기고 `tickErrors`로 집계한다. Colyseus는 미처리 예외가 나면 프로세스를 종료한다.
- `/metrics` 비동기 라우트도 예외를 잡는다. 처리되지 않은 Promise 거부는 Node에서 치명적이다.
- 원인을 알 수 없는 종료가 한 번 있었다(로그 없음). 그 뒤 프로세스 단위 예외·종료 로깅을 추가했고, 재현되지 않았다.
